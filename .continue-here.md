## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|----------------------|
| Split progress UI | Progress label renders ABOVE the URL input field AND optimistic row shows in the KB list simultaneously — two separate status areas for one job, confusing the user | blocking | Consolidate: progress should live ONLY inside the optimistic KB row. Remove the banner above the input entirely. |
| Silent stream drop | Stream ends without terminal event → shows "Upload submitted — refresh to see status" → user must manually refresh | blocking | Replace with polling: when stream ends without `job.complete`, start a `refetchInterval` on the documents query until `parse_status` leaves `pending`/`processing` |

### Root cause hypotheses (investigate in this order)

1. **uvicorn SSE keepalive timeout** — does uvicorn close the response after some idle period during a long Celery task? Check if the backend SSE endpoint sends keepalive comments (`:\n\n`) while waiting for events. If not, the connection may time out at the HTTP layer before `job.complete` fires. Look at `apps/api/app/api/v1/jobs.py` or wherever the SSE endpoint is.

2. **Two status areas rendering simultaneously** — `page.tsx` has BOTH:
   - A `progressLabel` banner rendered above/near the URL input (search for `submitting && progressLabel`)
   - An `optimisticDocs` row in the KB list showing the same label
   These are independent UI elements. The user sees both. Fix: **remove the banner above the input entirely** — let the optimistic KB row be the only progress indicator.

3. **"Upload submitted — refresh to see status"** fires when `teardown()` runs without `sawTerminal=true`. This means the stream dropped. Fix: after teardown with no terminal event, start polling — set `refetchInterval: 3000` on the documents query until all docs have `parse_status !== 'pending'` and `parse_status !== 'processing'`. The KB list will then update automatically.
