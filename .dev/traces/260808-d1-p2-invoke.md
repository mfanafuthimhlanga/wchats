## Decisions, and why this shape

**`agent_invoked` is an observation, written twice.** The `eval_runs` row is also the per-agent
idempotency key (`m6:{agent_id}`, 10-minute window), so it must exist before the first of sixty SDK
turns — inserting it afterwards would let a second beat dispatch double-invoke and double-bill. It is
therefore inserted carrying `agent_invoked=false` and corrected by `update_eval_run_config` once the
invocation has reported. Every failure between the two leaves the run claiming **less** than it did,
so the deploy gate P3 builds refuses it. The correction lands **before** scoring: the invocation is the
expensive, unrepeatable half and a judge outage must not take the record of what the agent did with it.

**`agent_invoked` is a conjunction, deliberately.** It means *the scored responses came from real agent
turns* **and** *enough rows answered to be a measurement*. A run where six of sixty scenarios answered
did invoke the agent and measured nothing; a gate reading a bare "we called it" would ship on it. The
raw fact stays readable at `agent_invocation.attempted`, so the two claims are separable — they are
just kept separate.

**Failure is exclusion, not a zero.** A turn that raised, timed out, or returned no text produces no
observation about answer quality. Averaging a zero in would move Faithfulness with the failure rate of
the Agent SDK, in the direction that reads as a quality regression. `compute_correlation.py:485`
learned this about a judge that errors; this is the same rule one layer earlier. `failed` and `empty`
are counted apart because an exception and a `max_turns` termination are different problems.

**The floor.** `MIN_RESPONSE_RATE = 0.8`, the same value and the same argument as
`compute_correlation.py:98`'s `MIN_PAIR_RATE`. Its absolute companion (`MIN_PAIRS = 3`) is deliberately
**not** duplicated: every figure here travels with its denominator, so a consumer wanting "at least N"
applies it to `responded` rather than to a second constant that can drift from the first.

**The truncation, made explicit rather than fixed.** `_run_sdk_turn` captures 1800 chars of a retrieve
result. Faithfulness over a cut context marks a claim unsupported when the support was merely beyond
the cap. The plan allowed either carrying the untruncated result on the eval path or recording the
truncation; **recording** was chosen because the alternative changes `_run_sdk_turn` on the chat path.
`retrieved_context_char_cap` and `retrieved_context_at_cap` (turns where a result came back exactly at
the boundary) are on every run. BACKLOG `2.13` carries the better fix.

**The canary is not re-rolled.** `build_eval_run_config` resolves the PRODUCTION prompt version for the
run's attribution; the turn re-fetches *that exact version's* soul fields through the same
`_resolve_turn_prompt_version` the chat path uses. Passing `soul_override=None` would have served the
agent's live `soul_*` columns while `eval_runs.prompt_version_id` still named the production version —
BACKLOG 2.3's defect exactly, which is why 2.3 closes here rather than being inherited.

**The branch is still unused, and that is not an oversight.** The turns run against the tenant's
PRODUCTION connection string because `retrieve` has to see the corpus the customer is served. What
stops them writing is **recorded mode**, not the branch. Two mechanisms for two jobs: a branch would
isolate a write, recorded mode prevents one — and the ProviderAdapter is outside the database
entirely, where no branch reaches.

**The PII firewall is NOT applied on the eval path**, and the run says so
(`agent_invocation.pii_firewall_applied: false`). A deflection is not an answer; scoring it would
measure the firewall's hit rate as if it were the agent's grounding. It is a real difference between
the text scored here and the text a customer reads, so it is recorded rather than left implicit.
BACKLOG `2.11`.

**Cost.** `AGENT_INVOCATION_CONCURRENCY = 1` (4 GB of RAM, one Agent SDK subprocess per turn) and the
loop **raises** if the constant moves without it, rather than recording a bound nothing enforced.
`AGENT_INVOCATION_MAX_CALLS_PER_RUN = 60`; worst case 60 × 90 s. Rows past the ceiling are reported
(`ceiling_skipped`, `ceiling_skipped_golden`), golden-first, never silently dropped.

## Anti-tautology: one guard was found proving a comment

`test_the_retrieve_cap_is_read_from_the_turn_path_not_copied` read `inspect.getsource(_run_sdk_turn)`
and asserted the constant's NAME appeared and `[:1800]` did not. Mutating the slice back to a literal
left it **green**: the name appears in the comment above the slice, and a reformatted literal is not
the substring `[:1800]`. Both halves were satisfied by prose.

That is BACKLOG 3.3's defect class — a guard demonstrated only inside the complement of its own blind
spot — and it was caught only because the mutation was actually run. Rewritten as
`test_the_turn_bounds_are_read_from_one_copy_of_the_number`, parametrized over both extracted
constants, reading the AST: a comment does not exist there and formatting cannot hide an integer. Both
parameters were then observed red.

**19 mutations were run, each observed red and then green after restoring from `HEAD`.** Verbatim
output: `.dev/reference/p2-mutation-proofs.md`.

## What was NOT proven

- **No end-to-end eval run was observed, and none can be on this machine.** There is no PostgreSQL
  server here; `CONTROL_DB_URL` is live Neon production and is never a substitute. Every
  `-m integration` harness still SKIPS, and a skip is unobserved, never a pass.
- **No live SDK turn ran.** The Agent SDK subprocess is doubled at one boundary in every test. Nothing
  here proves the seam's options are accepted by the real SDK, that `recorded` mode holds against a
  real ProviderAdapter, or that a real retrieve result is shaped the way the context extraction
  assumes.
- **`update_eval_run_config`'s SQL has never executed against a database.** The `||` merge is asserted
  at the call site only. Same standing debt as BACKLOG 3.5.
- **The metric has not been observed to move.** The whole point of this phase is that faithfulness
  should fall from ~1.0 to whatever is true, and that observation is behind BACKLOG `0.2`.
