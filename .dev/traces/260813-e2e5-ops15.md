# TRACE — E2E-5 · prove the gate refuses (2026-08-13). `5.1` CLOSED

**The API deployed an agent with an open critical red-team finding against it.** Observed, then
fixed, then re-observed refusing. `5.1` closed at `69f6fab`.

## The proof, before the fix

```
run_deployment_checklist.complete  recommendation=ship
deployment.approved  agent_id=eda2d887-…  run_id=a91af729-…
Got 200, expected 422
```

The ordering is the whole point. The **existing** test drives `finding → checklist → approve`: the
checklist sees the finding, freezes `block`, guard 2 refuses. That ordering was always safe. E2E-5
drives the other one — **clean checklist → finding raised afterwards → approve** — which is what
happens when a red-team run finishes minutes after a checklist, or a human files a finding.

## Why it could not have worked

Not a missing `if`. **`red_team_findings` lives in the TENANT database; the approve route only ever
touched the CONTROL database.** It had nothing to read live findings with. That is why five guards
existed and none of them was this one.

`5.1`'s own note — *"fails closed, so not a security hole"* — was true of the **console**, which was
fixed to refuse. It was never true of the **API**, and any script, curl or CI job holding a tenant
key took this path.

## The fix

Guard 2b, placed immediately after the frozen-recommendation check because it is the live counterpart
of that same question. Three decisions worth keeping:

1. **It calls `_fetch_red_team_summary_sync` — the same function the checklist uses.** Not a second
   hand-written query. Two readers of one rule is precisely how approve-time and checklist-time
   answers drift apart, which is the shape of this defect; sharing the reader makes them agree by
   construction.
2. **Fail-closed in both directions.** An unreadable connection string refuses, because *"I could not
   check" is not "there is nothing to find"*. The two refusals carry different messages: "N critical
   findings are open" sends the owner to contain them, "could not verify" sends them to their
   database.
3. **Runs in a worker thread.** The reader is blocking psycopg2 and this is an async route.

The eval sibling of this hole was closed the same way at `8b124d4`. **`2.19` — a gate-version stamp
so a stored verdict cannot outlive the rules that produced it — is still the better general fix and
stays open.**

## Two process failures of mine, both instructive

### The first mutation proof was invalid

To reach the fail-closed branch I mutated the route to fail *open* **and** reverted the unit fixture's
token in the same step. **Green in both states.** The two changes compensated, so I observed nothing.
The repo's existing standing rule caught it: a green that demands an explanation and hasn't got one is
not evidence.

**What it exposed is worse than the bad proof: nothing tested that branch at all.** I had written,
reviewed and committed a fail-closed path no test reached.
`TestApproveFailsClosedWhenLiveFindingsCannotBeRead` exists because of this.

### The replacement test passed for the wrong reason

Second attempt, one change only — and only **one** of the two new tests went red. The other asserted
`status_code == 422`, and this route has **five guards, every one of which returns 422**. It was
being satisfied by envelope drift. Fixed by matching the run's envelope hash to the live projection
so guard 4 cannot fire, and by asserting the detail message.

Both are now in `retro.md` as **Family K**, with the rule: *in a handler with more than one refusal
path, a status-code assertion has not identified the refusal — assert the reason.*
