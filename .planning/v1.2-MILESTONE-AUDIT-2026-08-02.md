# Milestone v1.2 — Audit Report

**Milestone:** v1.2 — Gotham console + comprehensive agent management (Phases 20–21)
**Audited:** 2026-08-02
**Status:** `gaps_found`

## The headline

Both phases pass their own verification. Neither phase did anything wrong. **The milestone
still does not deliver what it promised**, because the work that connects them was never
assigned to anyone.

Phase 20 built the console, including a six-region operations room shipped with *honest*
empty states for regions whose backends did not yet exist. Phase 21 then built those
backends — 16 requirements, 9 plans, `21-SECURITY.md` 33/33 threats closed. Phase 21's own
verification states it was a *"backend-only phase, no frontend artifacts."*
`.planning/AGENT-MGMT-GAPS.md` states the split explicitly: *"Phase 20 ports the UI; Phase 21
builds the missing backends."*

Both statements are true. Neither phase owned the seam between them, and **no phase ever ran
the wiring pass.** An empty state that was honest in Phase 20 became a false statement in
Phase 21.

This is the same defect class Phase 21's own verifier already caught once inside the phase —
the grade→promote dispatch, where plan 21-05 shipped in Wave 1 before 21-06 created the task
in Wave 3, so the later plan should have owned the wiring and didn't. `STATE.md` records the
lesson: *"when a seam crosses waves, the LATER plan must own the wiring."* The same failure
recurred one level up, across **phases** instead of waves, and the lesson did not scale with it.

### WIRE-02 (high) — real data rendered as absent

`evals.py:99,179-187` computes and returns `born_in_production_count` and `authored_count` on
the **same response the Judgement region already fetches**. The frontend's `EvalRunSummary`
interface (`page.tsx:47-59`) does not declare the fields, and lines 462, 467 and 488 hardcode
`not tracked yet`. The ORRERY ledger is sitting in the payload, unread.

### WIRE-03 (high) — the console makes three false statements

| Line | Copy | Reality |
|---|---|---|
| 405 | "Retrieval health instrumentation ships in a future release." | Shipped — OPS-05/06/07/08 |
| 548 | "Per-strategy coverage detail ships in a future release" | Shipped — OPS-13 |
| 587 | "Version history, canary releases and rollback ship in a future release." | Shipped — OPS-16 |

This is worse than an unwired region. A blank panel is silent; this actively tells the
operator a capability does not exist when it does. For a project whose stated core value is
being *defensible*, the console asserting a falsehood about its own capabilities is the most
serious finding in this audit after WIRE-01.

### WIRE-04 (high) — a block with no console-side release

OPS-15 works: `deployment_service.py:216-263` reads `red_team_findings WHERE status='open'`,
drives `recommendation='block'`, and `deployment.py` returns 422 on `POST /approve-deployment`,
which `deploy/page.tsx:2338-2341` surfaces. An operator is correctly stopped.

But OPS-14's `contain` action (`red_team.py:414`) has no trigger anywhere in the console. The
operator is blocked, correctly, and has no console-side way to clear it. Only the blocking half
of the chain is user-reachable.

## Requirements-register defects

**`OPS-01..06` is a live ID collision.** The same traceability table asserts both:

- line 274: `| OPS-01 | Phase 10 | M10 — Maintenance + Observability | Pending |`
- line 415: `| OPS-01..16 | Phase 21 — Agent-management backend completion | ✓ Complete |`

They are different requirements. M10's OPS-04 is "Langfuse v4 **dashboards**"; Phase 21's
OPS-04 is "extend Langfuse v4 **tracing** to the agent turn." Both mention Langfuse, which
makes them easy to confuse in exactly the way that produces a wrong tick. This project has
already had three requirement checkboxes found wrong (VER-01, AUD-03, ACT-04), each caught only
by reading source. An ID collision is a standing generator of that error.

**v1.2's 24 requirements have no checkbox-level definitions.** Only two roll-up rows exist.
`REQUIREMENTS.md:433` records this as deliberate, so it is a known shortcut rather than a
silent omission — but it means no per-requirement status can be tracked, which is why the
reachability gap above had to be stated separately from the requirements table.

## Verification method

Every claim in this audit was checked against source, not against planning documents. The
integration checker's findings were independently re-verified by the orchestrator: the
zero-caller greps, the OPS-12 payload-vs-render mismatch, the three "future release" strings,
the absence of widget feedback code, and the OPS-15 chain were each re-run directly. This
follows the project's own standing anti-pattern list — documents here have asserted work that
did not ship on at least four occasions.
