# Milestone v1.2 — Audit

**Gotham console + comprehensive agent management.** Phases 20, 21, 23.
(Phase 22 is *not* in this milestone — it belongs to v1.1 completion.)

**Status: `gaps_found`.** This supersedes the 2026-08-02 audit, preserved at
`v1.2-MILESTONE-AUDIT-2026-08-02.md`.

## What changed since the last audit

The 2026-08-02 audit found the milestone incomplete: both Phase 20 and Phase 21 passed
their own verification and all 24 requirements were satisfied at phase-acceptance level,
yet **only 11 of 24 were reachable by a user.** Phase 20 shipped the six-region operations
room with honest empty states for backends that did not exist; Phase 21 built those
backends as an explicitly *"backend-only phase, no frontend artifacts"*; neither phase
owned the seam.

**Phase 23 closed that seam.** All six regions now call their own Phase 21 endpoint,
`check-ops-room-wiring.mjs` exits 0 at 11/11 (independently re-run three times this
session), all three false "ships in a future release" claims are gone, the ORRERY ledger
renders counts it was already receiving, and the widget captures feedback at 8968/20480
bytes. The bench flywheel — complete on the backend since Phase 21 and never once
reachable by a human — has a UI entrance.

## The gap this audit found

**The same defect class recurred, one page over.**

Phase 23 fixed the deploy gate on the operations room: `page.tsx:384` now computes
`redTeamBlocked = isGateBlocked(openFindings)` fresh on every render, replacing a frozen
per-run JSONB snapshot that a `contain` action never updated.

`apps/admin/app/agents/[id]/deploy/page.tsx` was never touched — byte-unchanged across
the phase, as `23-06-SUMMARY.md` states outright. It carries its own independent copy of
the original defect:

```
deploy/page.tsx:2389  const redTeamBlockedSignal = report?.red_team_summary?.deployment_blocked === true
deploy/page.tsx:2395  const gateBlocked = checklistBlocked || redTeamBlockedSignal
```

`report` is a `checklist-runs` row computed once at checklist time by
`deployment_service.py:253`. A grep of the deploy page for `open_findings`,
`isGateBlocked`, or `red-team/programme` returns **zero hits** — it never sees the live
signal Phase 23 introduced.

**Severity, stated precisely rather than inflated.** The server-side gate
(`deployment.py:348+`) refuses approval on `run.recommendation == "block"` — also
snapshot-derived, also blind to live findings. So this **fails closed**: nobody can deploy
past a blocked checklist run. It is not a security hole.

What it is, is a **false-status contradiction**. Contain the last open critical finding and
the operations room reports the gate open while the deploy page and the server both still
report it blocked, until the checklist is re-run. Two surfaces disagree about one gate, and
nothing on screen explains why. That is precisely the class of defect this milestone
already failed an audit over.

**Phase 23 did not introduce this** — the snapshot-based deploy path predates it. Phase 23
*exposed* it by fixing one of the two surfaces. The remedy is a closure phase, not a
Phase 23 defect report.

The inverse case is worth naming too: a critical finding raised *after* a clean checklist
run leaves both the deploy page and the server permitting deployment, because
`run.recommendation` is still not `block`. That is an OPS-15 design property inherited from
Phase 21, not a regression.

## Closure progress

**2026-08-05 — the deploy-gate contradiction is closed in the console (`3701b05`).**
`deploy/page.tsx` now queries `/red-team/programme` and derives its gate through the same
`isGateBlocked` / `firstCriticalFinding` / `gateMessage` functions the operations room uses,
so the two surfaces cannot drift again by construction. The Red team ledger row, the
consequence sentence, the Approve reason chain and the accessible description were all moved
onto the live signal in the same pass, after an adversarial review found each of them still
answering from the frozen snapshot.

Both directions are handled, and deliberately not symmetrically:

- **staleClear** — a live critical shuts the gate and disables Approve. The console is now
  **stricter than the server on purpose.**
- **staleBlock** — the gate correctly stays shut (the server will refuse until the checklist
  re-runs) and the page now says why.

**What this does NOT close.** `POST /approve-deployment` still gates only on the frozen
`run.recommendation` and never consults live `open_findings`. A critical finding raised after
a clean checklist run is still accepted **by the API**, and any non-console caller — script,
curl, integration — can still deploy over it. The console can no longer be used to do it,
which removes the realistic path, but OPS-15's server-side enforcement gap is unchanged and
stays open. Closing it means teaching `deployment.py` to re-read open findings at approval
time, which is a backend change with its own threat surface and belongs in a planned phase.

**Still open from this audit:** the OPS-15 server gap above, and the `WIRE-01..05` /
`OPS-01..06` traceability gaps in `REQUIREMENTS.md`.

## Recommended closure

One phase closes the blocker and the traceability gap together:

1. Port `isGateBlocked` / `firstCriticalFinding` / `gateMessage` (already pure, in
   `opsFormat.ts`) into `deploy/page.tsx`, so both surfaces derive the gate from one source.
   Decide explicitly whether the server should also consult live `open_findings`, or whether
   "re-run the checklist" stays the deliberate contract — and if it stays, say so on screen
   rather than leaving the operator with two contradictory answers.
2. Add `WIRE-01..05` rows to `REQUIREMENTS.md`, correct the stale v1.2 rollup sentence, and
   resolve the `OPS-01..06` collision.
