<objective>
Build AUD-03's zero-audit-gap gate: a synthetic 30-day window of mutating traffic in
which every dispatcher invocation attempted has exactly one `tool_calls_audit` row,
on rejection branches as well as success.

Purpose: AUD-01 already asserts the per-call guarantee at unit level. AUD-03's "30 days"
is that guarantee integrated across realistic volume and time spread — the failure it
is designed to catch is a row silently dropped by a retry, a worker restart, or a Redis
blip, which a single-call unit test cannot see. The construction is fixed by
`19-01-PLAN.md § OD-3`: seeded backdated rows via direct SQL against an ephemeral
control DB, because `write_audit_row` has no `created_at` parameter and no clock seam
exists anywhere in `apps/api`.

The arithmetic is deliberately factored out of the DB-touching code so it can be proven
without Postgres — the gated harness is `autonomous:false` in effect (it needs real
local Postgres and Redis), and a phase whose only proof is a test nobody ran is exactly
the failure mode this plan's unit companion exists to prevent.

Output: `apps/api/tests/integration/test_aud03_audit_gap.py`,
`apps/api/tests/unit/test_audit_gap_arithmetic.py`.
</objective>

**Open Decisions:** all five are recorded in `19-01-PLAN.md § Open Decisions Resolved`.
OD-3 (seeded backdated rows; no clock injection) binds this plan.

    **`compute_audit_gap(invocations, audit_rows, *, window_start, window_days=AUDIT_WINDOW_DAYS)`**
    — a pure function with no DB access, no I/O, and no `app.*` dependency, so it is
    unit-testable against hand-built fixture data. Inputs are two sequences of mappings
    each carrying a timezone-aware `created_at` datetime; `invocations` additionally
    carries `skill`. It returns a mapping with these keys:
    - `per_day` — an ordered mapping keyed by `datetime.date`, one entry for every day
      from `window_start`'s UTC date through `window_days - 1` days later inclusive.
      Days with no traffic are present with zeroes; a missing key is never how a zero
      day is represented. Each value carries `invocations`, `audit_rows`, and
      `delta` (`audit_rows - invocations`).
    - `total_invocations`, `total_audit_rows`, `max_abs_delta`, `days_with_traffic`.
    - `out_of_window` — counts of `invocations` and `audit_rows` whose timestamp fell
      outside `[window_start_utc_date, +window_days)`. These are reported, never dropped.
    - `vacuous` — True when `total_invocations == 0`.
    Bucketing rule, stated in the function's docstring because it is the correctness
    crux: every timestamp is converted with `astimezone(timezone.utc)` first and then
    reduced to `.date()`. Both sides of the comparison use the identical rule, so a row
    written at 23:59 UTC and a row written at 00:01 UTC fall on adjacent days and never
    on both. A naive datetime is a programming error — raise `ValueError` naming the
    offending field rather than guessing a timezone.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| harness → control database | The harness writes and then rewrites `created_at` on audit rows; if pointed at the wrong database it forges audit history. |
| dispatcher invocation → audit row | The boundary AUD-03 exists to measure: one attempted invocation must produce exactly one row, on every branch. |
| test process → provider network | Probe-driven invocations could reach a real provider if the red-team short-circuit fails to engage. |
