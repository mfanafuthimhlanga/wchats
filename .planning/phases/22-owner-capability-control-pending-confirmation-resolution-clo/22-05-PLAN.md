    **2. Rewrite the Enabled subsection's second paragraph entirely.** Delete every sentence

    field, and the claim that a skill is switched on only by a direct database action outside

    - Every skill still ships off, and nothing acts on a customer's behalf until it is turned

    - You can now turn a skill on yourself, from the deploy screen, with no request to
      anybody. Quote the two resting captions verbatim from the screen.

      staged question, the primary button label and the secondary button label verbatim, and
      explain the reason in one sentence: for a live agent the change takes effect on the
      agent's very next customer turn, with nothing else in between.
    - If your agent has not been approved for deployment yet, the box saves immediately — the
      checklist and the approval step still stand between the change and any customer.
    - Turning a skill off is unchanged: it saves immediately in both cases, because disabling
      is always safe.

    **3. Correct the tighten-only section.** Its opening sentence — that the first change you
    make to a skill is compared against the platform default so you can never start looser
    than the platform allows — is now true of the bounded dimensions and false of the Enabled
    control. Add a short, explicit paragraph saying so: the ceiling, the rate limit and the
    Actor review mode are still compared against the platform default on a first write and can
    never start looser; the Enabled control is the one field the platform default no longer
    bounds in either direction, because it is a permission you hold rather than a limit the
    platform sets. State plainly that turning a skill on does not reset, raise, or unlock any
    other setting on that skill — every ceiling and limit you configured before disabling it
    is still exactly where you left it.

    **4. Add a new section headed `When an action needs your approval`,** placed after the
    tighten-only section and before the shipped-starting-point section. It must cover, in
    plain language:

    - What a pending confirmation is: an action the agent wanted to take that was held back
      for a person to decide, appearing under the pending-confirmations heading on the same
      deploy screen, below the capability panel.
    - What each row tells you: what the agent wants to do and for how much, when it was asked,
      and when the request expires. Quote the empty-state heading verbatim.
    - What approving does: the action runs once, in the background, shortly after you approve.
      Quote the approve confirmation's sub-line verbatim.
    - What rejecting does: the action never runs. Quote the reject sub-line verbatim.
    - What expiry does: a request that passes its deadline before anyone acts on it cannot be
      approved afterwards and never runs. Quote the expired-row caption verbatim. Do not
      promise that expired rows are tidied away automatically — no sweep ships in this phase
      (OD-2); the screen shows them as expired and refuses to act on them.
    - The honest outcome states: right after you approve, a row reads as approved and awaiting
      execution — quote that help text verbatim — and it becomes either executed or not
      executed once the action has actually been attempted.
    - **Why an approved request can still be refused.** If you tightened the ceiling, lowered
      the rate limit, or turned the skill off after the request was made, the checks run again
      against your current settings at the moment it tries to run, and it will be refused.
      That is the intended behaviour, not a fault: an approval granted under looser settings
      never executes under them. Quote the three denial translations verbatim.
    - **What approving does not do.** State it plainly: approving a request authorises the
      action. It does not verify the customer's identity. If a skill requires identity
      verification, the customer was verified when they originally made the request, and
      approving it later does not check that again (OD-1). This is a real consequence of how
      approval works, and the guide states it rather than leaving the reader to assume
      otherwise.
    - Two people, or two browser tabs, resolving the same request: the first one wins and the
      second is told so. Quote the concurrent-resolve note verbatim. It is expected, not an
      error.

    **5. Extend the friction section.** The existing paragraph — that lowering Actor review or
    turning identity verification off is never the right response to friction, and that
    presenting a safety control as an obstacle would be presenting it wrongly — stays exactly
    as it is. Add one paragraph in the same voice covering the two new surfaces: enabling a
    skill is a decision to grant an authority, so the right question is whether the agent
    should hold it at all, never whether turning it on would make a refusal go away; and
    approving a pending request is a decision about that one action, never a way to bypass a
    limit, and never a substitute for verifying who you are dealing with.

    **6. Update the enforcement and references sections.** Add the new backing modules with
