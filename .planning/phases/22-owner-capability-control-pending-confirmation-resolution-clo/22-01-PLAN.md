<objective>
Close CAP-05's backend half: make `enabled` an owner-controlled authorization toggle
instead of a tightness dimension bound by a permanently-`False` platform default, and
prove that the other five dimensions of `validate_tighten_only` are bit-for-bit as
strict as they were.

Purpose: `validate_tighten_only` rejects every `enabled: False -> True` transition
because every `PLATFORM_CAPABILITY_DEFAULTS` entry ships `enabled: False`, and no code
path in `apps/api/app/` sets `enabled=True`. A skill is switched on today only by direct
database action, which is exactly what VER-01 SC2 asserts a non-technical owner must not
need. This is the first of VER-01 SC2's two structural blockers.

Output: a six-line deletion in `capability_service.py`, and a test suite that proves the
deletion did not widen anything else.
</objective>

### OD-1 — Identity verification is NOT re-checked at resolution (`22-RESEARCH.md § Open Decisions (a)`)

**Resolved: skip the IDV gate at resolution, explicitly, and accept the residual as a
named threat (`T-22-ACT-08`, severity medium, disposition accept).**

This is a security decision, not a technicality, so it is stated plainly: for a skill
carrying `requires_identity_verification: true`, the customer's identity was verified
when the request was originally made, and it is **not** verified again when an approver
clicks Approve hours later. What is authorized at approval time is the action; the
customer's identity is not re-attested at that moment.

Three facts make skipping the only honest option:

1. `verified_session_token` is a per-turn `ContextVar` (`apps/api/app/services/agent_tools.py`),
   never persisted to any table a resolver could query. There is nothing to re-check.
2. The approver is an admin, not the customer. Auto-issuing a synthetic "verified on the
   customer's behalf" session so the gate passes would be a genuine IDV-05 regression —
   approving a money-moving action and verifying a customer's identity are different
   acts, and conflating them would make the audit trail assert something false.
3. Requiring the customer to re-verify out of band before an approver may act needs a
   third row state ("approved, awaiting customer re-verification") that is modelled
   nowhere, plus a customer-facing re-verification prompt with no delivery channel
   outside a live turn. That is a materially larger scope than CAP-05/ACT-07, and it is a
   **missing-information / dependency** constraint, not a difficulty judgement.

Two facts bound the residual, and both are source-anchored rather than reassuring prose:

- **Ordering.** Step 2.5 (IDV) precedes step 5 (Actor) in `_execute_transactional_tool`
  (`tools.py:208-301` before `tools.py:401`). Every `require_human` row for an
  IDV-requiring skill was therefore created by a call that held a valid verified session
  at creation time. The gap is staleness of that session, never its absence.
- **Window.** `_CONFIRM_TTL_HOURS = 24` (`tools.py:101`) bounds the staleness window to
  24 hours: `expires_at` is stamped at creation and the resolve path refuses an expired
  row (plan 22-03).

The decision is made mechanically enforceable rather than left as prose: plan 22-02's
`confirmation_resolution.py` must never import or reference `check_verified_session`, and
an `inspect.getsource`-style absence test asserts it, alongside the equivalent assertion
for `call_actor_gate`. A future change that quietly re-adds an IDV call — or, worse, a
synthetic session — trips a red test.

### OD-2 — Expiry is lazy only; no sweep task ships in this phase (`22-RESEARCH.md § Open Decisions (b)`)

**Resolved: enforce expiry lazily inside the resolve route's atomic claim. No Celery
sweep is built.**

`expires_at` already exists on `pending_confirmations` (`pending_confirmation.py:37`), so
this is enforcement, not schema. The lazy construction is strictly stronger than a sweep:
it holds even if a sweep never runs, and an unresolved expired row that nobody ever
clicks Approve on never executes by construction. A sweep would be queue hygiene only —
and its own live-DB proof would be unrunnable in this environment, adding an
`autonomous:false` gate that buys no correctness.

The one thing a sweep would have bought — an approver not staring at a three-week-old row
labelled "Pending" — is bought instead by two shipped behaviours: the GET queue route
drops rows resolved more than 24 hours ago, and the UI performs a client-side `expires_at`
check that renders `Expired` and disables Approve/Reject ahead of any server sweep
(`22-UI-SPEC.md` § UI Considerations, `expired-but-unresolved` row, already ✅ covered).

This is a deliberate, named scope exclusion, not a silent omission. Follow-up (a
`pipeline`-queue sweep marking expired-and-unresolved rows `resolution='expired'`) is
logged to STATE.md by plan 22-06.

### OD-3 — Execution outcome is a read-time lookup against `tool_calls_audit`; there is no `0020` migration (`22-RESEARCH.md § Open Decisions (c)`, `22-UI-SPEC.md` § Surface 2)

**Resolved: no new column, no `0020` migration. The GET queue route computes an
`execution_outcome` for `resolution='approved'` rows by reading the resolver's own audit
row.** This closes the UI-SPEC's `unresolved` execution-outcome item and, with it, its
second `unresolved` item (`error (denial reason)`), which had the same single root cause.

`22-PATTERNS.md` confirmed the complete column list (`id, agent_id, skill, arguments,
requested_at, expires_at, resolved_at, resolution`) — there is no field distinguishing
"approved and executed" from "approved but denied at execution when the live envelope had
since been tightened," and no unread column hiding one. The two real options were a `0020`
migration or a read-time join. The join wins on three grounds:

1. **The audit row is already a complete record by construction.** The resolver writes
   exactly one `tool_calls_audit` row on every terminal outcome (T-22-ACT-06, AUD-01
   symmetry). A denormalized column would be a second source of truth for the same fact,
   able to drift from the audit trail — the failure mode `Don't Hand-Roll` warns about.
2. **The join key exists and is precise.** `tool_calls_audit` carries `agent_id`, `skill`,
   `arguments` (JSONB, containing `idempotency_key`), `actor_decision`, `error`, and
   `created_at` (`tool_calls_audit.py:36-59`), with an index on `(agent_id, skill)`. The
   resolver stamps `actor_decision="approved_by_human"`, which is what distinguishes its
   row from the ORIGINAL `require_human` row written at creation time — that original row
   shares `agent_id`, `skill` and `arguments` and would otherwise be a false match.
3. **No live control DB exists here.** A `0020` up/down roundtrip is an unrunnable
   `autonomous:false` operator gate (control head is `0019`,
   `alembic/versions/0019_blast_radius_capability_v2.py`). Choosing the join keeps this
   phase's proof surface entirely within the unit suite.

The resolved contract, locked for plans 22-03 and 22-04:

| Lookup result | `execution_outcome` | UI |
|---|---|---|
| no matching audit row | `null` | `mute` chip `Approved`, help text `Awaiting execution.` (the UI-SPEC's honest fallback, still reachable — the task has not run, or the enqueue failed) |
| row with `error IS NULL` | `"executed"` | `pass` chip `Executed` |
| row with non-null `error` | `"not_executed"` + `execution_error` carrying the raw string | `fail` chip `Not executed` + the UI-SPEC's denial translation, keyed off the `capability.denial:` prefix |

### OD-5 (planner-surfaced, not in RESEARCH) — the resolver's execution-context shim is an explicit parameter contract, not ContextVar seeding

`22-VALIDATION.md § Wave 0` requires that whatever stands in for the dispatcher's four
ContextVar-sourced values be "a named, tested artifact — not incidental setup inside a
route handler."

**Resolved: thread `agent_id` and `conn_str` as explicit function parameters; do not seed
ContextVars at all.** Reading the four functions the narrow resolver actually calls,
every one of them already takes what it needs explicitly:
`check_capability_access(agent_id, skill)`, `apply_rate_and_constraint_checks(agent_id,
skill, snapshot, args)`, `reserve_idempotency(agent_id, skill, key, args_hash)`,
`get_adapter_for_skill(skill, agent_id, conn_str)`, `write_audit_row(agent_id=...,
conn-free)`. The ContextVars are read **only** by `_execute_transactional_tool`'s own
prologue (`tools.py:150-160`). A steps-2/3/4/6/7 subset that takes parameters therefore
needs no `build_tool_server()` call, which is simpler and strictly safer than the
`red_team_probe.py` seeding pattern `22-PATTERNS.md` offered as the fallback — there is no
ambient state to leak between a resolver task and anything else in the worker process.

The named artifact is the parameter contract on `execute_approved_confirmation`:
`agent_id` and `conn_str` come from the claimed row plus
`fernet_decrypt(agent.neon_connection_string)`; `conversation_id` is a fresh `uuid4()`
generated inside the resolver (informational on the audit row, never a join key back to a
real chat); and `verified_session_token` has **no** substitute and is structurally absent
because step 2.5 is not re-entered (OD-1). It is tested: a source-absence assertion proves
`confirmation_resolution.py` references none of `_agent_id_var`, `_conn_str_var`,
`_conversation_id_var`, `_verified_session_token_var`.

### OD-6 (planner-surfaced) — commit the claim BEFORE enqueueing, overturning the research snippet

`22-RESEARCH.md § Code Examples` and `22-PATTERNS.md` both show `.delay(...)` called
before `await db.commit()`. **Overturned: commit first, enqueue second.** A task
dispatched before the claim commits can be picked up by a worker that reads the row in its
pre-claim state — unresolved, or absent from the worker's snapshot entirely — and would
either no-op or act on a state the route has not yet made durable. Committing first makes
the only remaining window the one `22-RESEARCH.md` already names and accepts: the enqueue
itself failing after a durable claim (`T-22-ACT-09`, disposition accept). Plan 22-03
asserts the ordering directly.
