Ship ACT-07's control surface: the approver's queue read, the atomic resolve claim, and
the `runtime`-queue task that performs the approved execution.

Purpose: `pending_confirmations` rows are written by two code paths and read by none. This
plan gives them a resolver — one that claims the row in the database rather than in
application logic, enforces expiry inside that same statement, and hands the actual
provider call to Celery because a FastAPI request handler must never make it.

Output: `pending_confirmation.py` schemas, `pending_confirmations.py` routes,
`confirmations.py` Celery task, both registrations, and the route-level unit file.
</objective>

    Route 1 — `GET /agents/{agent_id}/pending-confirmations`. Guard first. Then return, in
    this exact order:

    - every row with `resolved_at IS NULL`, ordered by the deadline ascending with nulls
      last, then by `id` ascending;
    - then every row resolved within the last 24 hours, ordered by resolution time
      descending, then by `id` ascending.

    Rows resolved more than 24 hours ago are excluded — this is a triage queue, not an audit
    trail, and a full history view is explicitly out of scope (`22-UI-SPEC.md § Ordering`
    closes the research's Open Question 2 this way). The `id` tiebreak in both groups is
    load-bearing, not decoration: without it two rows sharing a deadline can swap position
    between requests, and a queue that reorders under the approver's cursor is a mis-click
    waiting to happen.

    Then, for each row whose resolution is the approved value, compute the execution outcome
    with one lookup against `tool_calls_audit` (OD-3). Match on four predicates: the agent
    id, the skill, the arguments' idempotency key extracted with the JSONB text operator,
    and an actor decision equal to the human-approval marker the resolver writes. Order by
    `created_at` descending, limit 1. Extract this into a module-private
    `_execution_outcome_for(...)` so it is one named, testable unit rather than inline route
    logic.

    The actor-decision predicate is the discriminator and must not be dropped: the original
    approval-required audit row written at creation time shares the agent id, the skill and
    the arguments with this one, and matching it would report an execution that never
    happened. Map the result: no row → `execution_outcome` is `None` (the honest awaiting-
    execution state the UI renders); a row with a null error → `"executed"`; a row with a
    non-null error → `"not_executed"`, with `execution_error` set to the raw string and
    `executed_at` to that row's `created_at`. Skip the lookup entirely for rows whose
    resolution is not the approved value — a rejection has no execution and no denial code,
    and asking for one would be the conflation `22-UI-SPEC.md § Contradictions` corrects.

    Log once on success: `log.info("list_pending_confirmations.ok", agent_id=...,
    tenant_id=..., row_count=...)`. Never log a row's arguments — they carry customer email,
    shipping address and amounts.

    Route 2 — `POST /agents/{agent_id}/pending-confirmations/{confirmation_id}/resolve`,
    body `PendingConfirmationResolve`. Guard first, before touching the confirmation id or
    the body. Then the atomic claim, a single `UPDATE pending_confirmations` statement that
    sets `resolved_at` to the database clock and sets the resolution via a CASE expression
    forcing the expired value when the row has a non-null deadline that is strictly less
    than the database clock, scoped by `WHERE id = :id AND agent_id = :agent_id AND
    resolved_at IS NULL`, and returning the id, skill, arguments, requested-at, deadline,
    resolved-at and resolution columns.

    Three properties of that statement are locked and each has a test:

    - The deadline comparison is a strict less-than, so a row resolved at exactly its
      deadline is not expired and resolves as requested. The boundary instant belongs to the
      approver. This mirrors how this codebase already pins a strict threshold on both sides
      (the Actor skip's strict comparison against its cents threshold).
    - The non-null conjunct on the deadline means a row with no configured deadline is never
      expired. That column is nullable and a null must not silently become a refusal.
    - `resolved_at IS NULL` in the WHERE clause is the entire concurrency control. A `None`
      from `.mappings().first()` means the row was already resolved, does not exist, or does
      not belong to this agent — raise 409 with a detail that does not distinguish those
      cases. 409 rather than 404 is correct here because it fires only after the
      ownership-guarded check has already passed, so it leaks nothing across tenants.

    Then `await db.commit()`. Only after the commit returns, and only when the claimed
    resolution is the approved value AND the claimed skill is a key of `SKILL_INPUT_MODELS`,
    dispatch the execution task with the confirmation id as its sole argument. Two notes on
    that ordering and that condition:

    - Commit-then-dispatch overturns the ordering shown in `22-RESEARCH.md § Code Examples`
      and `22-PATTERNS.md` (OD-6). A task dispatched before the claim is durable can be
      picked up by a worker that reads the row in its pre-claim state. Committing first
      leaves exactly one accepted window — the dispatch failing after a durable claim,
      recorded as `T-22-ACT-09`, disposition accept, matching every other Celery-dispatching
      route in this codebase.
    - The `SKILL_INPUT_MODELS` membership test is what keeps a non-mutating confirmation-skill
      row — which has no adapter method and no idempotency key — from ever being handed to
      the execution task. Such a row is still resolvable; it simply executes nothing, because
      there was never anything to execute.

    Import the Celery task lazily inside the function body if a module-level import would

    surrounding `api/v1/` modules already do for task dispatch and do not invent a third

    function's own docstring forbids a route-handler call site, and a route that resolved

    Log once on success: `log.info("resolve_pending_confirmation.ok", agent_id=...,
