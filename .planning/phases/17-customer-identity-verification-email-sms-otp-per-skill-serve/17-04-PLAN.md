<objective>
Build `identity_service.py` — the deterministic, server-side OTP engine for Phase 17. It generates
and hashes codes and session tokens with the `secrets`/`hashlib`/`hmac` stdlib primitives (the
`security.py` convention), stores ephemeral challenge state in Redis with a TTL (OD-3), delivers the
code over email (SMTP, `escalation.py` fire-and-forget pattern) or SMS (a provider seam defaulting to
Twilio, OD-2), and — on a correct single-use code — issues a short-lived verified session persisted
as a SHA-256 hash in the tenant-DB `customer_identities` table. It also exposes
`check_verified_session`, the tenant-DB lookup the Step 2.5 enforcement gate (17-06) calls.

Purpose: This is the IDV-02 (email OTP) + IDV-03 (SMS OTP) engine and the service half of IDV-05
(verified-session check). All security invariants (single-use, attempt lockout, constant-time
compare, hash-at-rest, server-issued token) live here in plain Python — never in agent judgment.
Output: `identity_service.py` + `test_identity_service.py`.

Locked decisions recorded here:
- OD-2: SMS default = Twilio behind a `SmsProvider` Protocol; `AfricasTalkingProvider` +
  `NullSmsProvider` also implemented; selected at call time from `settings.SMS_PROVIDER`.
- OD-3: OTP challenge state in Redis (TTL), single-use (delete-first on success).
- OD-4: session TTL = `settings.VERIFIED_SESSION_TTL_SECONDS` (3600s global).
- OD-5: `external_id` = delivery address; normalized before use (lowercased email; E.164 phone).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pre-auth customer → OTP service | The customer is unverified when requesting/submitting a code |
| service → Redis / tenant DB | Ephemeral challenge state in Redis; durable session hash in the tenant DB |
| service → SMS/email provider | Code leaves the trust boundary only via the controlled delivery channel |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-04 | Elevation of Privilege | verify_otp brute force | mitigate | OTP_MAX_ATTEMPTS=5 lockout + 6-digit space + short TTL; wrong code increments attempts |
| T-17-05 | Repudiation | OTP replay | mitigate | Single-use: Redis key DELETED before session issuance (delete-first, Pitfall 4) |
| T-17-06 | Information Disclosure | code/session compare timing | mitigate | `hmac.compare_digest` for all code and hash comparisons |
| T-17-07 | Elevation of Privilege | session fixation | mitigate | Token generated server-side via `secrets.token_urlsafe(32)` only after a correct code; client cannot inject its own |
| T-17-08 | Information Disclosure | code/token at rest | mitigate | SHA-256 hash stored (Redis challenge hash + `session_token_hash`); raw values never persisted or logged |
| T-17-01 | Elevation of Privilege (IDOR) | check_verified_session | mitigate | Query runs against the tenant `conn_str` only; per-tenant scope (OD-1), no cross-tenant hash reuse |
| T-17-18 | Denial of Service | SMS cost via request_otp | mitigate | Per-external_id send limit (OTP_SEND_MAX_PER_WINDOW) in Redis; per-IP + JWT enforced at the route (17-05) |
| T-17-SC | Tampering | twilio at import | mitigate | Provider import is lazy; version pinned + human-verified in 17-02 |
</threat_model>
