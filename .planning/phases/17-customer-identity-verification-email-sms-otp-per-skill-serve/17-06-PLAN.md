<objective>
Land the server-side enforcement that is the point of the whole phase: a new Step 2.5 in
`_execute_transactional_tool` that, when the capability snapshot has
`requires_identity_verification=true` (IDV-04, read from the envelope snapshot already fetched in
Step 2 — no extra DB call), requires a valid verified session before the mutation proceeds (IDV-05).
It reads `_verified_session_token_var` and calls `check_verified_session` against the tenant DB. The
gate is deterministic Python that runs BEFORE the agent's tool ever touches a provider — the agent's
prose is irrelevant and cannot bypass it.

Purpose: IDV-04 (envelope-driven per-skill requirement) + IDV-05 (server-side, never-from-prose
enforcement). Placed BEFORE reserve_idempotency (Step 3) so a rejected unverified call never burns
the idempotency slot — the customer can verify and retry with the same idempotency_key.
Output: Step 2.5 in tools.py + the IDV enforcement tests.

Critical ordering + audit invariants (locked):
- Step order: capability check (2) -> IDV gate (2.5) -> reserve idempotency (3). Never after (3).
- AUD-01 symmetry: both block branches call `write_audit_row` exactly once with error
  `identity_verification.required` (no token) or `identity_verification.invalid_or_expired`
  (token present but invalid/expired), mirroring the `capability.denial` branch.
- Circular-import safety: import `check_verified_session` and `_verified_session_token_var` lazily
  inside the function body (the file's existing convention).
</objective>
