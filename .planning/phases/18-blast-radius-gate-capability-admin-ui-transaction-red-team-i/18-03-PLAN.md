<objective>
Build the substrate that makes RTX-01/02/03 meaningful: a probe path that drives the **real**
`_execute_transactional_tool` dispatcher, with provider resolution short-circuited to
`StubProviderAdapter` so no live Stripe/Shopify/WooCommerce/Calendly call ever fires during a
red-team run.

Purpose: this is the single most load-bearing decision in Phase 18. The shipped `_build_probe_fn`
(`apps/api/app/worker/tasks/runtime/red_team.py:99-117`) is a bare
`_ANTHROPIC_CLIENT.messages.create(...)` call with **no `tools=` kwarg at all** — no dispatcher, no
capability envelope check, no IDV gate, no idempotency reservation, no Actor seam. It tests whether a
persona can be talked into *saying* something. It cannot test whether a mutating tool call *executes*.
If RTX-01..03 reused it, RTX-04's "zero high-severity findings" would be a vacuous claim: the probes
would pass because nothing was ever attempted.

**Higher-uncertainty task warning.** `18-PATTERNS.md` names three no-analog gaps and two of them are
in this plan: `_build_transactional_probe_fn`, and the red-team-mode short-circuit in
`get_adapter_for_skill`. RESEARCH.md's Pattern 2 code sketch is explicitly labelled `[ASSUMED]` and is
not verified existing code. Expect to iterate; the mocked-boundary unit tests in Task 3 are the
feedback loop.

Output: `_red_team_mode_var` + the short-circuit in `provider_adapter.py`, a new
`app/services/red_team_probe.py` carrying the probe surfaces and the executable clean-tenant posture,
and `tests/unit/test_red_team_probe.py`.

**Decisions:** see `18-01-PLAN.md` § Open Decisions Resolved — this plan implements **OD-6**.

## Verified facts about the code this plan touches

- `get_adapter_for_skill(skill, agent_id, conn_str)` is `async`, lives in
  `app/services/transactional/provider_adapter.py:206`, and its **first** action is
  `config = await _fetch_credential_config(conn_str, skill)`, raising `ProviderNotConfiguredError`
  when it returns `None`. It is called from exactly one place: `tools.py:492`, step 6 of
  `_execute_transactional_tool`.
- `StubProviderAdapter` is already built (`provider_adapter.py:110-183`), returns `[STUB]`-labelled
  Output objects for all six mutating methods, makes no network calls, and a module-level singleton
  `_STUB_ADAPTER` plus a `get_adapter(agent_id=None)` factory already exist at lines 190-200.
- The dispatcher reads its context from ContextVars **defined in `app/services/agent_tools.py`** and
  imported lazily inside the function body to break a circular import
  (`tools.py:150-155`): `_agent_id_var`, `_conn_str_var`, `_conversation_id_var`,
  `_verified_session_token_var`. `_tenant_id_var` is read the same way inside
  `provider_adapter.py:254`.
- `build_tool_server(conn_str, agent_id, agent_name, strategy, conversation_id, notify_fn, tenant_id="", verified_session_token="", job_id="")`
  (`agent_tools.py:693`) sets **all** of those ContextVars and returns the MCP server registering 11
  tools. It is the sanctioned way to populate probe context — do not set the ContextVars by hand.
- The real customer turn builds its SDK options as
  `ClaudeAgentOptions(model=..., system_prompt=..., mcp_servers={"customer-tools": tool_server}, allowed_tools=["mcp__customer-tools__issue_refund", ...], resume=..., max_turns=6, max_budget_usd=...)`
  (`app/worker/tasks/runtime/agent.py:840-864`). MCP-registered `@tool` handlers therefore **do** work
  through `ClaudeSDKClient`; the Phase 9 constraint is about *custom JSON tool schemas passed inline*,
  which is why `classify_severity`'s forced-tool-use judge uses the direct Anthropic API instead.
- The existing sync/async bridge that already works in this codebase:
  `run_X_agent` calls `asyncio.run(...)`, and inside that loop it calls
  `await asyncio.to_thread(probe_fn, msg)`; `probe_fn` then calls its own `asyncio.run(...)` on a
  fresh thread with no running loop. A nested-SDK probe reuses that exact bridge.

**(a) `red_team_mode()`** — a `@contextlib.contextmanager` that calls
`provider_adapter._set_red_team_mode(True)`, yields, and calls `_reset_red_team_mode(token)` in a
`finally`. This is the only sanctioned setter. Docstring records that it must wrap every probe
invocation and nothing else.

**(b) `PROBE_SKILL_TOOLS`** — a dict mapping each of the six mutating skill names plus
`confirm_action` to the corresponding `@tool` object imported from
`app.services.transactional.tools`. Import inside the function or at module level as the circular-import
situation allows (`tools.py` already imports `agent_tools` lazily inside function bodies, so a
module-level import of `tools` from this new module is safe — verify by importing the module).

**(c) `resolve_probe_handler(skill: str)`** — returns `getattr(tool_obj, "handler", tool_obj)` for

`getattr` fallback is required in production code, not just tests: whether `@tool` yields the function
or an `SdkMcpTool` dataclass depends on which `claude_agent_sdk` was imported first.

**(d) `ProbeToolResult`** — a frozen dataclass with `skill: str`, `is_error: bool`, `text: str`, plus a

one window. Docstring records that the caller must have already populated the dispatcher ContextVars
via `build_tool_server` and must hold an open `red_team_mode()` window.
