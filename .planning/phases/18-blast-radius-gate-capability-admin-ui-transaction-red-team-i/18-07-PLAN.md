<objective>
Close BLR-02 and CAP-04: record the envelope hash on every completed checklist run, surface drift on the
checklist read, gate `POST /approve-deployment` with a 422 when the live configuration no longer matches
what the run recorded, and stamp the acknowledgement.

Purpose: CAP-04 requires that "any later envelope change re-triggers the pre-deployment checklist
(acknowledged via envelope hash)". The mechanism is not to mutate history — `checklist_runs` is an
immutable audit trail, the same principle migration `0018_prompt_versions` established. Instead the live
hash is compared against the recorded one: advisory on read, enforced at approve.

Output: `_compute_envelope_hash_sync` in `deployment_service.py`, hash persistence in the checklist task,
the fourth approve-time validation plus acknowledgement stamping plus `envelope_drift` on the read
payload in `api/v1/deployment.py`, and the two test cases 18-VALIDATION.md pins by name.

**Decisions:** see `18-01-PLAN.md` § Open Decisions Resolved — this plan implements **OD-2**.

**Cross-wave seam ownership:** plan 18-04 created `canonical_envelope_hash` and `envelope_drift` with no
callers, and plan 18-05 added the fifth collector. **This plan is the later, calling plan and owns every
one of these call sites**, and its acceptance criteria assert each one exists. That is the explicit
correction of the Phase 21 failure recorded in `.planning/.continue-here.md`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated owner → `POST /approve-deployment` | A human act flips an agent live in front of every customer. |
| live `capability_envelopes` rows → an approval recorded earlier | The configuration can change between the checklist run and the approval. |
| one tenant's session → another tenant's agent | Every agent-scoped route must not leak existence. |
| `checklist_runs` history → the deploy decision | History is an audit trail and must not be rewritten to make an approval possible. |
