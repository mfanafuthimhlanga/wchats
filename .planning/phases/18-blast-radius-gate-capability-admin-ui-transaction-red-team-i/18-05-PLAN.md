<objective>
Add the fifth M8 signal collector: the financial blast-radius gate (BLR-01). It is architecturally
different from the four shipped collectors — it reads the **control DB** via `get_sync_db()` rather
than the tenant DB via `psycopg2.connect(conn_str, ...)`, because `capability_envelopes`,
`tool_calls_audit` and `tenants` all live in the control DB.

Purpose: BLR-01 is the number a non-technical owner is asked to accept financial risk against. It
reports what the owner has **authorized** and what has actually **happened**, as separate claims.

Output: `_fetch_blast_radius_sync` and `derive_blast_radius_warnings` in `deployment_service.py`, a
`blast_radius` field on `DeploymentReport`, the Step 4 wiring plus deterministic warning merge in the
Celery task, and unit coverage in both existing test modules.

**Decisions:** see `18-01-PLAN.md` § Open Decisions Resolved — this plan implements **OD-1** (four
separately-labelled numbers, `None` never coerced to `0`) and **OD-1b** (per-tenant threshold columns
with platform-default fallback, and the warning derived in Python rather than by the orchestrator LLM).

**(a) `BLAST_RADIUS_DEFAULT_SIGNAL`** — a module-level dict with every signal key present and honest
values: all four figures `None`, `enabled_skill_count` `0`, `observed_window_days` from
`settings.BLAST_RADIUS_OBSERVED_WINDOW_DAYS`, and the two threshold keys from the platform-default
settings. This is the fallback the Celery task substitutes when the collector raises, matching the
shape of the four existing safe-default dicts. Note in a comment that `None` is deliberate: a fallback
of `0` would assert "this agent's largest authorized action is nothing", which is a false measurement
rather than a missing one.

**(b) `_resolve_blast_radius_thresholds(agent_id: str) -> tuple[int, int]`** — reads the owning
tenant's threshold columns by joining `agents` to `tenants` on `agents.tenant_id`, returning
`(single_cents, hourly_cents)` with `COALESCE` semantics applied in Python: a NULL column falls back to
`settings.BLAST_RADIUS_WARN_SINGLE_CENTS` / `settings.BLAST_RADIUS_WARN_HOURLY_CENTS`. Uses
`with get_sync_db() as db:` and a single parameterised `text()` SELECT. On no row found, return the two
platform defaults.

**(c) `_fetch_blast_radius_sync(agent_id: str) -> dict`** — signature takes **only `agent_id`**; it must
not accept `conn_str`. Docstring opens by stating that this is the one signal collector that reads the
**control DB** via `get_sync_db()` rather than the tenant DB via psycopg2, because
`capability_envelopes`, `tool_calls_audit` and `tenants` are control-DB tables, and that it therefore
needs no tenant connection string at all (CLAUDE.md rule 4 satisfied by construction). All SQL is
parameterised `text()` with a single `:agent_id` bind.

Four figures, computed inside one `with get_sync_db() as db:` block:

- `configured_max_single_action_cents` — `MAX((constraints->>'max_amount_cents')::int)` over
  `capability_envelopes` rows for the agent with `enabled = true`. **Additionally**: if any enabled row
  has a NULL or absent `max_amount_cents`, the configured single-action ceiling is unbounded, so return
  `None` rather than the max of the bounded rows. Implement this as a second scalar query counting
  enabled rows whose `constraints->>'max_amount_cents'` IS NULL; a non-zero count forces `None`. This is
  what makes UI-SPEC D4.2's "No ceiling" verdict honest — a partially-bounded configuration is not a
  ceiling.
- `configured_max_hourly_aggregate_cents` — the worst-case hourly exposure the owner has authorized,
  derived per enabled skill as `max_amount_cents * calls_per_hour` where `calls_per_hour` comes from
  parsing `rate_limit` (`max_calls * 3600 / window_secs`), then summed across enabled skills. Reuse
  `_parse_rate_limit` by importing it from `app.services.transactional.enforcement` (the same import
  plan 18-04 uses). If any enabled skill has a NULL `rate_limit` or a NULL `max_amount_cents`, the
  hourly aggregate is unbounded, so return `None`. Round up to the nearest whole cent with `math.ceil`
  so the figure never understates authorized exposure.
- `observed_max_single_action_cents` — `MAX(COALESCE((arguments->>'amount_cents')::int, (arguments->>'refund_amount_cents')::int))`
  over `tool_calls_audit` rows for the agent with `error IS NULL` and
  `created_at > now() - (:window_days || ' days')::interval`. A query returning NULL (no qualifying
  rows) yields `None`, never `0`.
- `observed_max_hourly_aggregate_cents` — the max over hour buckets of the summed successful amounts in
  the same window: a subquery grouping by `date_trunc('hour', created_at)` and summing
  `COALESCE((arguments->>'amount_cents')::int, (arguments->>'refund_amount_cents')::int, 0)`, then
  `MAX(hourly_total)` over that. NULL yields `None`.

Also return `enabled_skill_count` (the count of enabled envelope rows), `observed_window_days` from
settings, and the two resolved threshold values from `_resolve_blast_radius_thresholds`. Docstring lists
every returned key with its meaning and states explicitly that a configured `None` means "no ceiling
configured" while an observed `None` means "never observed", and that these are different claims that
callers must not collapse (UI-SPEC D4).

Do **not** wrap the body in a broad `try/except` — the four existing collectors are wrapped by the
caller in the Celery task, and this one must follow the same convention so a failure is logged with the
task's own event name and fallback.

**(d) `derive_blast_radius_warnings(blast_radius: dict) -> list[DeploymentWarning]`** — pure function,
no DB, no LLM. Returns:
- `blast_radius_no_ceiling_configured` (`category="financial_exposure"`, `severity_level="warning"`)
  when `enabled_skill_count > 0` and `configured_max_single_action_cents` is `None` — an unconfigured
  ceiling on an agent that can move money is real exposure.
- `blast_radius_single_action_above_threshold` (`category="financial_exposure"`,
  `severity_level="warning"`) when `configured_max_single_action_cents` is not `None` and strictly
  exceeds `warn_threshold_single_cents`.
- `blast_radius_hourly_aggregate_above_threshold` (same category and severity) when
  `configured_max_hourly_aggregate_cents` is not `None` and strictly exceeds
  `warn_threshold_hourly_cents`.
- An empty list when `enabled_skill_count == 0` — an agent with no enabled transactional skill has no
  blast radius to warn about.
Each message is plain-language for a non-technical owner, sentence case, hyphen not em dash, naming the
rand figure and the threshold it exceeded (cents divided by 100, two decimals). The messages must
distinguish the ceiling from the observed maximum in their wording — never present one as the other
(UI-SPEC D3). Never emit a warning derived from an **observed** figure: an observed value describes
history, not current authorization, and warning on it would ask the owner to acknowledge a risk they
may already have tightened away.

**(e) `DeploymentReport.blast_radius: dict`** — a new field, placed after `corpus_stats`, documented as
the raw signal from `_fetch_blast_radius_sync`. Give it a default of an empty dict so any existing
construction site that has not been updated still validates.

**(f) `_DEPLOYMENT_SYSTEM_PROMPT`** — add the blast-radius signal to the orchestrator's awareness for
**narrative purposes only**. Add a short paragraph naming the `blast_radius` signal keys and
instructing the orchestrator that it may reference the configured ceiling and the observed maximum in
its plain-language `summary`, that it must keep them as separate claims, and that it must **not** emit a
warning for blast radius because the platform derives that warning itself. Do not add blast radius to
the blocking-conditions list. Record in a comment that a financial gate must not depend on an LLM
performing an arithmetic comparison (CLAUDE.md: programmatic core, agentic edges), and that this split
is what prevents a duplicate warning appearing twice in `run_obj.warnings`.
