**(a) `PLATFORM_CAPABILITY_DEFAULTS`** — a module-level dict with **exactly 7 keys**: the six mutating
skill names plus `confirm_action`. Every value is a dict carrying **all seven** of the same keys, so no
consumer ever has to guard against a missing field: `enabled`, `rate_limit`, `constraints`,
`requires_confirmation`, `requires_identity_verification`, `actor_mode`, `mutating`.

*The six mutating entries* (`place_order`, `cancel_order`, `issue_refund`, `update_subscription`,
`book_slot`, `update_customer_record`): `mutating: True`, `actor_mode: "always-on"`, `enabled: False`
(the platform default is fail-closed, matching `capability_envelopes.enabled`'s `server_default=false`
and the T-14-01-01 schema-level decision), `requires_confirmation: False`,
`requires_identity_verification: False`, `rate_limit: "5/hour"`, and a conservative
`constraints: {"max_amount_cents": N}` with N = `100000` for `place_order` and `50000` for the other
five.

*The `confirm_action` entry* — state it fully and concretely rather than by exception, because it is the
one entry whose field set is easy to leave half-specified:
- `mutating: False` — it is the only non-mutating skill, and the only skill for which
  `actor_mode = "off"` is ever legal (PRD §4.5).
- `enabled: False` — same fail-closed default as the six.
- `rate_limit: "20/hour"` — a real value, not `None`. A confirmation tool is called more often than a
  mutation but is still rate-bounded, and `validate_tighten_only`'s `rate_limit` branch treats a
  proposed `None` against a non-`None` current as `loosen_rate_limit_removed`, so giving it a real
  ceiling keeps that branch meaningful for this skill instead of leaving it permanently at the loosest
  possible value.
- `constraints: {}` — an **empty dict**, explicitly **not** `{"max_amount_cents": ...}` and explicitly
  not `None`. `confirm_action` moves no money: it writes a `pending_confirmations` row and calls no
  provider adapter, so a monetary ceiling on it is a control that means nothing. An empty dict keeps the
  key present and JSON-serialisable for the canonical hash while asserting there is no monetary bound to
  configure. `validate_tighten_only`'s `max_amount_cents` branch reads a missing key as `None` (no
  ceiling ever configured), which is the correct semantics here.
- `requires_confirmation: False` and `requires_identity_verification: False`.
- `actor_mode: "always-on"` — the strictest legal value, so the default is not `"off"` merely because

**Consumer contract, recorded in the module docstring:** `mutating` is the flag every consumer uses to
decide whether a skill has a monetary/transactional surface at all. Plan 18-08's GET returns one entry
per key (7 entries, so the response shape is stable and complete), and plan 18-10's capability panel

in the UI without a second edit.

Docstring also records **OD-3**: these live here rather than in `config.py` because `Settings` is a flat
scalar surface, pydantic-settings would attempt env parsing of a nested per-skill dict, and no env
override is wanted; and that a per-tenant configurable defaults table is deliberately deferred as
premature for seven skills and one tenant class.

**(b) `HASHED_ENVELOPE_FIELDS`** — a tuple naming exactly the seven semantic fields in a fixed order:
`("skill", "enabled", "rate_limit", "constraints", "requires_confirmation", "requires_identity_verification", "actor_mode")`.
Docstring records **OD-2**: `id`, `agent_id` and `updated_at` are excluded because they are
DB-managed and non-semantic, and including `updated_at` would make a no-op re-save produce a new hash,
firing false drift warnings that desensitise the owner to real changes (RESEARCH Pitfall 2).

**(c) `ACTOR_MODE_RE`** and `parse_actor_mode(value: str) -> tuple[int, int]` — `ACTOR_MODE_RE` compiles
`^sample_at_rate_([1-9][0-9]?|100)$`, matching `ck_capability_envelopes_actor_mode` exactly.
`parse_actor_mode` returns a `(tier, rate)` tightness pair: `("off" -> (0, 0))`,
`("sample_at_rate_N" -> (1, N))`, `("always-on" -> (2, 0))`. Comparison is lexicographic on the pair,
so `off` < any sampled mode < `always-on`, and within the sampled tier a higher N is tighter. Raise
`ValueError` on any value outside the domain — an unparseable mode must be a hard error, not a silent
"treat as loosest", because the loosest interpretation would let an invalid write through the
comparator.

**(d) `canonical_envelope_payload(rows: list[dict]) -> str`** — build a list of lists by projecting each
row onto `HASHED_ENVELOPE_FIELDS` in that exact order, sort the outer list by the `skill` value, and
serialise with `json.dumps(payload, sort_keys=True, separators=(",", ":"), default=str)`. `sort_keys`
covers the nested `constraints` dict; `separators` removes whitespace variance; `default=str` makes a
`Decimal` or `datetime` that leaks into `constraints` serialise deterministically instead of raising.
Rows missing a field are projected with `None` for it rather than raising, so a row read from a DB that
predates 0019 still hashes (it simply hashes as having no `actor_mode`).

**(e) `canonical_envelope_hash(rows: list[dict]) -> str`** — `hashlib.sha256(payload.encode("utf-8")).hexdigest()`
over `canonical_envelope_payload(rows)`. For an empty row list, return the hash of the canonical empty
payload — a deterministic value, not the empty string and not `None`, so "this agent has no envelopes"
is a hashable state rather than a null that downstream drift logic would have to special-case.

**(f) `validate_tighten_only(current, proposed, platform_defaults=None) -> str | None`** — the CAP-03
gate. Returns `None` when the proposed envelope is at-or-tighter than `current` on every field, or a
short snake_case reason string naming the first violated field otherwise, mirroring
`check_capability_access`'s reason-string convention. `platform_defaults` defaults to
`PLATFORM_CAPABILITY_DEFAULTS` when `None`. Only fields **present** in `proposed` are compared
(partial PATCH semantics); an absent field is not a change. Emit a
`log.warning("capability.tighten_only_rejected", skill=..., reason=..., field=...)` on every rejection
branch before returning, matching `enforcement.py`'s structured-denial convention. Never log the
proposed values themselves.

Per-field rules — implement each as its own early-return branch:
- `enabled`: `True -> False` is always allowed (disabling is always tighter). `False -> True` is
  allowed **only** when the platform default for that skill has `enabled: True`; otherwise return
  `loosen_enabled`. Since every platform default ships `enabled: False`, the practical effect is that
  re-enabling a disabled skill is not reachable through this route — record that consequence in the
  docstring so it is a chosen behaviour rather than a surprise.
- `rate_limit`: parse both sides with `_parse_rate_limit`. A proposed `None` (no limit) against a
  non-`None` current is `loosen_rate_limit_removed`. A malformed proposed value is
  `invalid_rate_limit`. Otherwise compare `max_calls / window_secs` as a float rate: a strictly greater
  proposed rate is `loosen_rate_limit`. Equal is allowed. This makes a unit switch (`"10/day"` to
  `"10/hour"`) correctly a loosen, because rate-per-second rises.
- `constraints.max_amount_cents`: a proposed `None`/absent-key against a non-`None` current is
  `loosen_max_amount_removed`. A proposed value strictly greater than current is
  `loosen_max_amount_cents`. When current is `None` (no ceiling ever configured) any proposed value is
  allowed, including another `None`. Compare only this key; other `constraints` keys are not part of
  the tighten-only comparison in v1.1 and must pass through unexamined — record that in the docstring.
- `requires_confirmation`: `False -> True` allowed; `True -> False` returns `loosen_requires_confirmation`.
- `requires_identity_verification`: `False -> True` allowed; `True -> False` returns
  `loosen_requires_identity_verification`.
- `actor_mode`: compare `parse_actor_mode(proposed)` against `parse_actor_mode(current)`; a strictly
  looser pair returns `loosen_actor_mode`. A `ValueError` from `parse_actor_mode` on the proposed value
  returns `invalid_actor_mode`. Additionally: `"off"` is rejected with `actor_mode_off_requires_non_mutating`
  whenever the skill's platform-default entry has `mutating: True` — for a mutating skill, `off` is not
  a valid state at any tightness level, not merely one the owner may not reach right now (PRD §4.5).

**(g) `envelope_drift(live_hash, acknowledged_hash) -> bool`** — returns `True` when
`acknowledged_hash` is `None` or empty, or when it differs from `live_hash`. Docstring records the
contract plan 18-01's threat register handed down: a `NULL` `checklist_runs.envelope_hash` on a
historical run means **drift** (nothing was ever acknowledged), never "matches whatever is live now".
Also returns `True` when `live_hash` is `None` — an uncomputable live hash is not evidence of a match.

Module docstring records that this file is deliberately caller-free: the call sites live in plan 18-07
(checklist task, approve route, checklist read) and plan 18-08 (the PATCH route), and each of those
plans asserts its own call site.
