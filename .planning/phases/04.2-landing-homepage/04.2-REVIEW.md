## Summary

Nine files were reviewed across the admin Next.js app: one deploy page, two stub pages (eval, ingest), one agent-journey page, one create-agent wizard, one agents-dashboard page, and three shared components. The stack is Next.js 14 (App Router) with Clerk for auth.

The most serious finding is an **unvalidated custom font URL that is saved to the API and could be reflected into a `<link>` or `<style>` tag by the widget loader** — a stored XSS / CSS-injection vector. Two additional blockers exist: a missing `getToken` dependency in `useEffect` that silently breaks authentication on re-renders, and an unchecked `data.agents` shape that crashes the agents dashboard when the API returns a non-array.

Seven warnings cover missing ARIA attributes on tab panels, an array index used as React list `key`, a polling interval that can run forever if the component unmounts mid-flight between the `clearInterval` call and the `router.push`, stale-closure risk in the poll callback, missing `loading` state on `setLoading(false)` when auth fails early, and a dead code path in `deriveStepState`.

## Critical Issues

### CR-01: Custom font URL saved to API without validation — stored XSS / CSS injection vector

**File:** `apps/admin/app/agents/[id]/deploy/page.tsx:557-578`

**Issue:** The "Custom Font URL" input accepts any string and sends it verbatim to `POST /api/v1/agents/{id}/widget-config`. If the widget loader on the customer's site uses this value to dynamically inject a `<link rel="stylesheet" href="...">` or `@import url(...)`, an attacker who can reach the deploy page (any authenticated admin) can supply a `javascript:` URI or a CSS file from an attacker-controlled server containing `}body{display:none}` (CSS injection) or worse. Even within the admin UI itself, the value is read back from the API and placed in React state — React's JSX escaping protects text nodes but does NOT protect `href` or `src` attribute injection if the widget ever renders a `<link>` using this value.

Validate the URL on the client before saving, and reject non-HTTPS URLs:

```typescript
// Before calling handleSaveDesign, or inside it:
const url = widgetConfig.typography.font_custom_url
if (url) {
  try {
    const parsed = new URL(url)
    if (parsed.protocol !== 'https:') {
      setSaveStatus('error')
      setLoadError('Custom font URL must use HTTPS.')
      return
    }
  } catch {
    setSaveStatus('error')
    setLoadError('Custom font URL is not a valid URL.')
    return
  }
}
```

The backend `POST /api/v1/agents/{id}/widget-config` must also enforce HTTPS-only and allowlist known font CDN origins (Google Fonts, Bunny, Adobe) or at minimum reject `javascript:` and `data:` schemes.

### CR-02: `getToken` missing from `useEffect` dependency arrays — stale closure silently uses wrong token

**File:** `apps/admin/app/agents/[id]/deploy/page.tsx:197-227` and `apps/admin/app/agents/[id]/page.tsx:77-97`

**Issue:** Both `useEffect` hooks call `getToken()` but omit it from the dependency array. In `deploy/page.tsx` this is suppressed with `// eslint-disable-line react-hooks/exhaustive-deps`. Clerk's `getToken` is a stable reference, so in practice this does not cause an infinite loop. However:

1. If Clerk ever replaces the `getToken` reference (e.g., after a session refresh), the stale closure continues calling the old function, silently using an expired token.
2. The blanket `eslint-disable` on line 227 suppresses ALL exhaustive-deps warnings for that hook, meaning future contributors who add dependencies will not receive a warning.

**Fix:** Add `getToken` to the dependency array. Clerk guarantees `getToken` is referentially stable, so this is safe and correct.

```typescript
// deploy/page.tsx line 227
}, [id, apiBase, getToken])

// [id]/page.tsx line 97
}, [id, apiBase, getToken])
```

Remove the `// eslint-disable-line` comment entirely.

### CR-03: `data.agents` access without shape validation crashes dashboard on unexpected API response

**File:** `apps/admin/app/agents/page.tsx:61-62`

**Issue:**
```typescript
const data = await r.json()
setAgents(data.agents)
```

If the API returns `{ "detail": "Not found" }` with a 2xx status code, or returns `{ "agents": null }`, then `setAgents(null)` is called. The subsequent render at line 155 calls `agents.map(...)` on `null`, throwing `TypeError: Cannot read properties of null (reading 'map')`, which produces an unhandled runtime crash (white screen in production).

**Fix:**
```typescript
const data = await r.json()
if (!Array.isArray(data?.agents)) {
  throw new Error('Unexpected response shape from /api/v1/agents')
}
setAgents(data.agents)
```

**File:** `apps/admin/app/agents/[id]/deploy/page.tsx:319-363`

**Issue:** The `role="tablist"` container holds two `role="tab"` buttons with `aria-selected`, but neither button has `aria-controls` pointing to its tab panel, and the tab panels themselves have no `role="tabpanel"` or `id`.   </div>

  <div role="tabpanel" id="panel-design" aria-labelledby="tab-design" ...>

### WR-02: Array index used as React `key` in mutable lists causes stale input state

**File:** `apps/admin/app/agents/[id]/soul/page.tsx:461, 543` (soul editor, read for context)

**Issue:** Both the Do List and Do Not List render items with `key={i}` (array index). When an item is removed from the middle of the list, React matches the old item at index `i` to the new item at index `i`, reusing the DOM node. Because these are controlled inputs this does not cause a visible stale-value bug today, but it does cause React to incorrectly reuse focus state and animations. This is a known React anti-pattern specifically warned against for mutable lists.

**Fix:** Assign stable IDs to list items (e.g., generated on `addDoItem`/`addDonotItem` with `crypto.randomUUID()`) and use those as `key`.

```typescript
type ListItem = { id: string; value: string }
const [soulDoList, setSoulDoList] = useState<ListItem[]>([{ id: crypto.randomUUID(), value: '' }])

// In render:
{soulDoList.map((item) => (
  <div key={item.id} ...>
    <input value={item.value} onChange={(e) => updateDoItem(item.id, e.target.value)} />
    <button onClick={() => removeDoItem(item.id)}>...</button>
  </div>
))}
```

### WR-03: Polling interval can fire after component unmount — state-update-on-unmounted-component

**File:** `apps/admin/app/agents/new/page.tsx:82-108`

**Issue:** The cleanup `useEffect` at line 29 clears `pollRef.current` on unmount. However, between the moment the poll callback calls `clearInterval(pollRef.current!)` (line 96) and the `router.push('/agents/' + createdAgentId)` call (line 98), React's navigation causes the component to unmount. Before the component fully unmounts, React may have already set `pollRef.current = null` (line 97), but if the interval fires one final time during the navigation transition, it can call `setStatus`, `setError`, or `setPhase` on the unmounted component, producing the React warning "Can't perform a React state update on an unmounted component."

**Fix:** Add an `isMounted` guard inside the poll callback:

```typescript
const isMountedRef = useRef(true)
useEffect(() => {
  return () => {
    isMountedRef.current = false
    if (pollRef.current) clearInterval(pollRef.current)
  }
}, [])

// Inside the poll callback:
const pollData: { status: string } = await pollRes.json()
if (!isMountedRef.current) return
setStatus(pollData.status)
```

### WR-04: Stale closure captures `createdAgentId` from outer scope — safe today, fragile pattern

**File:** `apps/admin/app/agents/new/page.tsx:87`

**Issue:** The poll interval callback closes over `createdAgentId` (a `const` declared in `handleSubmit`). This is safe because `createdAgentId` never changes, but the pattern bypasses React state (`agentId` is set at line 78 but never read by the poll). If a future change reads from `agentId` state instead of the closed-over variable, it will silently use `null` (the initial state) because `pollRef.current` captures the stale closure. This is a maintainability trap.

**Fix:** The poll callback should read from `agentId` state via a ref to avoid stale closure issues:

```typescript
const agentIdRef = useRef<string | null>(null)
// After setAgentId(createdAgentId):
agentIdRef.current = createdAgentId
// In poll callback, use agentIdRef.current
```

### WR-06: Dead code path in `deriveStepState` — step 2 can never return `'active'` with correct value

**File:** `apps/admin/app/agents/[id]/page.tsx:44-49`

**Issue:**
```typescript
const step2Done = step1Done  // identical assignment
...
case 2:
  if (!step1Done) return 'locked'
  return step1Done ? 'active' : 'locked'  // step1Done is always true here — second branch unreachable
```

Line 49 `return step1Done ? 'active' : 'locked'` is evaluated only when `step1Done === true` (the `if (!step1Done) return 'locked'` guard above ensures this). The ternary always resolves to `'active'`. The `'locked'` branch of this ternary is dead code. Additionally, `step2Done` is declared and unused as a distinct concept — it's always equal to `step1Done`, masking the intent.

This is not a crash, but it signals that the step-2 "done" state is never reachable from the UI (the Configure step can never show as "Done"), which is presumably a future implementation gap that should be tracked.

**Fix:**
```typescript
case 2:
  return step1Done ? 'active' : 'locked'
```

Remove `step2Done` or give it a real condition when the configure step has a completion signal.

### WR-07: `JourneyStepper` locked steps are non-interactive but have no `aria-disabled` — AT will try to activate them

**File:** `apps/admin/app/components/JourneyStepper.tsx:146-155`

**Issue:** Locked steps that have an `href` are rendered as plain `div` content (not a `Link`), which is correct. However, steps that have `href` and `state !== 'locked'` are wrapped in `Link`. There is no mechanism to communicate to assistive technology that locked steps are non-interactive. Keyboard users tabbing through the stepper will skip locked steps (they have no focusable element) — that part is fine. But `step.state === 'done'` steps with an `href` get a fully navigable `Link` with no indication that they are "already completed" or whether re-visiting is intended. The `done` badge says "Done" visually, but there is no `aria-label` or `aria-describedby` on the `Link` to communicate this to screen readers.

**Fix:**
```tsx
<Link
  href={step.href}
  style={{ textDecoration: 'none', color: 'inherit', display: 'block' }}
  aria-label={`${step.title} — ${step.state === 'done' ? 'completed' : 'in progress'}`}
>
  {rowContent}
</Link>
```

### IN-03: `AgentCard` renders `new Date(created_at).toLocaleDateString()` without locale or format options

**File:** `apps/admin/app/components/AgentCard.tsx:43`

**Issue:** `new Date(created_at).toLocaleDateString()` with no arguments uses the browser's default locale. On systems with non-US locales this produces `DD/MM/YYYY` or `YYYY年M月D日` etc., making the date format inconsistent across users. For a business product this should be deterministic.

**Fix:**
```typescript
const formattedDate = new Date(created_at).toLocaleDateString('en-GB', {
  year: 'numeric', month: 'short', day: 'numeric'
})
```
