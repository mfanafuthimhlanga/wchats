## Summary

Phase 4.2 builds the full admin UI shell for Veridian: a public landing page at `/`, an authenticated agent dashboard at `/agents`, a per-agent journey view at `/agents/[id]`, and stub pages for Ingest, Eval, and Deploy (the Deploy page implements a full widget customization panel, not a stub). The existing soul editor at `/agents/[id]/soul` is preserved with no changes.

The tech stack is fully determined: Next.js 16.2.6 App Router with TypeScript, `@clerk/nextjs` 7.3.5 for auth, and CSS custom properties via `globals.css` as the only styling mechanism. No new npm packages are needed — all required patterns (`useAuth`, `useUser`, `UserButton`, `usePathname`) are already present in installed packages. The project uses inline `style={}` objects referencing CSS variables throughout — no Tailwind classnames in component code.

The single biggest gap is the missing `GET /api/v1/agents` list endpoint — only `GET /api/v1/agents/{agent_id}` exists. The dashboard page needs to list all agents for the authenticated tenant, which requires a new backend route. The widget customization page also requires two new backend routes: `POST /api/v1/agents/{id}/widget-config` and `GET /api/v1/agents/{id}/widget-config`.

The `--bg` token in `globals.css` is currently `#FDF9F5` (wrong). UI-SPEC.md §5 and the locked mockup `layout-b-topnav.html` define `--bg: #F0E8E0`. This token must be corrected in `globals.css` before any new pages are built, as it affects every surface in the app shell.

**Primary recommendation:** Build in wave order — first fix globals.css + add TopNav layout + middleware, then the landing page, then the dashboard, then the journey view, then the stub pages with full deploy widget customization last.

### Pattern 1: Root Layout with TopNav Shell

The root `layout.tsx` is a **server component** that wraps all children with `<ClerkProvider>`. The `<TopNav>` component must be a **client component** (uses `usePathname` and Clerk hooks). The layout renders TopNav only for protected routes — the landing page `/` renders without it. The pattern is to use a conditional render based on whether the current path is `/`.

However, conditional rendering in `layout.tsx` based on pathname requires the layout to be a client component or use a nested layout. The correct Next.js App Router pattern is:

- Keep root `layout.tsx` as a server component with `<ClerkProvider>` only
- Wrap all protected routes in `app/agents/layout.tsx` — a client component that renders `<TopNav>` + `{children}`
- The landing page `/` uses root layout only (no TopNav)

This matches the Next.js nested layout pattern. [VERIFIED: Next.js App Router docs — each route segment can have its own layout]

```tsx
// app/agents/layout.tsx — NEW, client component
'use client'
import TopNav from '../components/TopNav'

export default function AgentsLayout({ children }: { children: React.ReactNode }) {
  return (
    <>
      <TopNav />
      <main style={{ minHeight: 'calc(100vh - 56px)', background: 'var(--bg)' }}>
        {children}
      </main>
    </>
  )
}
```

### Pattern 5: SSE for Agent Provisioning (create flow)

When `POST /api/v1/agents` returns `{ agent_id, job_id, events_url }`, the admin UI must follow the SSE stream to show provisioning progress:

```tsx
// EventSource — browser native API, no package needed
const source = new EventSource(`${apiBase}/api/v1${data.events_url}`)
// NOTE: admin uses /jobs/{id}/events (with X-API-Key or Authorization),
// not /widget/jobs/{id}/events (public path)
```

The admin client uses Bearer token auth. The existing `/jobs/{id}/events` endpoint requires `X-API-Key`. The admin now uses Bearer (Clerk JWT) — this was wired in Phase 04-10 (CORS now includes `Authorization` header). The EventSource API does NOT support custom headers — this is a known limitation. The solution used in the widget is the public `/widget/jobs/{id}/events` endpoint which requires no auth. For the admin create flow, either:
1. Use the same public widget SSE endpoint (already in `AgentCreateResponse.events_url` as `/jobs/{id}/events`)
2. Poll `GET /api/v1/agents/{id}` for status instead of SSE

Looking at the route: `AgentCreateResponse.events_url = f"/jobs/{job.id}/events"` — this is the authenticated path. EventSource cannot send Authorization headers. The admin create wizard should poll `GET /api/v1/agents/{id}` every 2 seconds until `status == 'ready'` rather than using EventSource with Bearer auth. This avoids the EventSource header limitation. [VERIFIED: agents.py line 97 — events_url uses /jobs/ not /widget/jobs/]

**Alternative:** Use `fetch()` with `text/event-stream` content-type and `ReadableStream` — allows custom headers. This is more complex but correct. For simplicity, polling is recommended for the admin create flow.

### Pattern 6: Inline Style Convention (matches existing codebase)

The existing soul/page.tsx uses **inline style objects** referencing CSS variables throughout. All new components must follow this same convention. No Tailwind class usage in component code (Tailwind is in devDependencies but the existing pattern is inline styles).

```tsx
// CORRECT — matches codebase pattern
style={{ background: 'var(--bg)', color: 'var(--text-1)', padding: '12px 16px' }}

// WRONG — Tailwind classes not used in component files
className="bg-parchment text-wine p-4"
```

### Anti-Patterns to Avoid

- **Using Tailwind classes in TSX components:** The existing soul/page.tsx uses zero Tailwind classes. All new components must match this pattern.
- **Using `--surface-1` for cards:** `--surface-1` is for form inputs only. Cards use `--surface-2`. Page backgrounds use `--bg`. This distinction is strict per UI-SPEC §5.
- **Importing `usePathname` from clerk:** It comes from `next/navigation`, not `@clerk/nextjs`.
- **Using EventSource for admin SSE:** EventSource cannot send `Authorization` headers. Use polling or fetch-based streaming for the create-agent flow.
- **Nested layout in root layout.tsx for nav:** Add TopNav in `app/agents/layout.tsx` — not in root layout — so landing page doesn't get the nav bar.
- **Missing `aria-current="page"` on active nav link:** UI-SPEC §10 requires this for accessibility.

## Common Pitfalls

### Pitfall 1: Wrong --bg Token

**What goes wrong:** Building all pages against `#FDF9F5` (current globals.css) instead of `#F0E8E0` (UI-SPEC canonical). The visual result is a lighter, less warm parchment that doesn't match the mockup.
**Why it happens:** globals.css was not updated when Design G was finalized.
**How to avoid:** Fix `globals.css --bg: #F0E8E0` in the very first task before building any pages.
**Warning signs:** Pages look lighter/cooler than the HTML mockup.

### Pitfall 2: Using --surface-1 for Cards

**What goes wrong:** Using `--surface-1` (#FFFCF9) for agent cards, stat cards, or substep cards — they appear too white and elevated incorrectly.
**Why it happens:** UI-SPEC's surface hierarchy is strict: `--surface-1` = form inputs ONLY.
**How to avoid:** Cards → `--surface-2`. Page/nav/section backgrounds → `--bg`. Inputs → `--surface-1`.
**Warning signs:** Cards look bleached white against parchment background.

### Pitfall 3: TopNav in Root Layout Breaks Landing Page

**What goes wrong:** Adding `<TopNav>` to root `layout.tsx` causes the landing page to render with the authenticated app nav.
**Why it happens:** Root layout wraps ALL routes including `/`.
**How to avoid:** Use a nested layout at `app/agents/layout.tsx` for TopNav — not root layout.

### Pitfall 4: EventSource Cannot Send Authorization Headers

**What goes wrong:** Attempting to stream `GET /jobs/{job_id}/events` with Authorization header using EventSource API fails silently.
**Why it happens:** The EventSource browser API does not support custom headers by spec.
**How to avoid:** For the create agent provisioning flow, use polling (`GET /api/v1/agents/{id}` every 2s until `status == 'ready'`) rather than SSE. Alternatively use `fetch()` with `ReadableStream` + `Authorization` header.

### Pitfall 5: Missing GET /agents List Endpoint

**What goes wrong:** Dashboard page tries to fetch agent list but `GET /api/v1/agents` returns 404 or 405.
**Why it happens:** Only `GET /api/v1/agents/{agent_id}` exists. There is no list endpoint.
**How to avoid:** Add backend route FIRST (Wave 1 or 2), then build the dashboard page against it. Do not build the dashboard UI and discover the missing endpoint later.

### Pitfall 6: Params Promise Pattern (Next.js 15+)

**What goes wrong:** Accessing `params.id` directly in a page component causes a TypeScript error or runtime warning in Next.js 15/16.
**Why it happens:** Next.js 15+ made route params a `Promise<{ id: string }>` in async contexts.
**How to avoid:** Follow the existing soul/page.tsx pattern exactly — use `use(params)` hook:
```tsx
export default function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = use(params)
```
[VERIFIED: soul/page.tsx lines 88–91]

### Pitfall 7: Widget Config -- Missing DB Migration

**What goes wrong:** `POST /api/v1/agents/{id}/widget-config` saves to a column that doesn't exist yet.
**Why it happens:** `widget_config` JSONB is a new column — not in existing migrations 0001–0008.
**How to avoid:** Add Alembic migration 0009 for `agents.widget_config JSONB DEFAULT '{}'::jsonb` before wiring the frontend.

## Backend API Additions Required

Three new backend items are needed for Phase 4.2:

### 1. GET /api/v1/agents — List Agents

Add to `apps/api/app/api/v1/agents.py`:
```python
@router.get("/agents", response_model=AgentListResponse)
async def list_agents(
    db: AsyncSession = Depends(get_async_db),
    tenant: Tenant = Depends(get_current_tenant),
) -> AgentListResponse:
    result = await db.execute(
        select(Agent)
        .where(Agent.tenant_id == tenant.id, Agent.deleted_at.is_(None))
        .order_by(Agent.created_at.desc())
    )
    agents = result.scalars().all()
    return AgentListResponse(agents=[AgentResponse.model_validate(a) for a in agents])
```

```python
    'widget_config', postgresql.JSONB,
    nullable=False,
    server_default=text("'{}'::jsonb")
))
```

### 3. GET/POST /api/v1/agents/{id}/widget-config

New routes in `agents.py` (or a new `widget_config.py` router):
- `GET /agents/{id}/widget-config` — returns `agent.widget_config` JSONB
- `POST /agents/{id}/widget-config` — validates JSON body against widget config schema, sets `agent.widget_config`, returns 200

Auth: Bearer JWT (same as PATCH). Both routes filter by `tenant_id` for ownership.

## Open Questions (RESOLVED)

1. **Polling vs SSE for create agent flow**
   - What we know: EventSource cannot send `Authorization` headers; the admin flow needs to show provisioning progress
   - What's unclear: Is a simple status polling UX (spinner + "Provisioning... checking every 2s") acceptable, or does the spec require real-time event streaming?
   - Recommendation: Use polling. The provisioning takes ~30 seconds. Polling every 2s is imperceptible to users and avoids EventSource header complexity.

2. **Widget config persistence: column on agents table vs separate table**
   - What we know: UI-SPEC §9 specifies `POST /api/v1/agents/{id}/widget-config` saves config JSON
   - What's unclear: Whether a dedicated `widget_configs` table or a column on `agents` is preferred
   - Recommendation: JSONB column on `agents` — simpler, consistent with `retrieval_strategy` pattern already on the agents table.

3. **Status color token update scope**
   - What we know: globals.css uses slightly different status color values than UI-SPEC §5
   - What's unclear: Does the soul editor's existing visual appearance depend on the current (incorrect) color values?
   - Recommendation: Update all tokens in the same Wave 1 task as the `--bg` fix. The soul editor's error states (`--red`) will shift from a slightly orange-red to a more pure red — acceptable visual improvement.
