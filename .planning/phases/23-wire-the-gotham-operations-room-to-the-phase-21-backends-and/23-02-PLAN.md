<objective>
Close Gap B: return the agent's open red-team findings, with their real primary keys, on the
programme read the Adversary region is already required to call. Without an identifier there
is nothing to contain, and INT-04 ships either a broken button or no button at all.

Purpose: `POST .../findings/{finding_id}/contain` has existed since Phase 21 and has never
had a caller, because no route anywhere surfaces a finding's identifier. The per-run findings
snapshot carries descriptions but no ids; the first-class table carries ids but no
description. Neither alone is enough, and the fix is one query plus a correlation, not a
column.

Output: a fourth query and a fourth response key in `read_programme`, and the tests that
prove it — including the three existing tests this change breaks.
</objective>

  <action>
    **The statement.** Add a fourth module-level statement constant beside the existing three,
    selecting the identifier, run identifier, strategy identifier, severity, attack vector,
    probe message, agent response, turn count and creation time from the findings table, left
    joined to the runs table so each row also carries its own run's findings snapshot, and
    filtered to the open status.

    Two properties of this statement are locked and each has a test:

    - **The severity ordering is a rank expression, not a plain descending sort on the
      column.** `23-PATTERNS.md` shows a descending sort on the severity column. That column
      is text, so a descending sort orders it lexically — medium, low, high, critical — which
      is very nearly the inverse of severity order and would put the critical finding, the
      only one that shuts the gate, last in the list. Use an explicit rank: critical, then
      high, then medium, then low; break ties on creation time, newest first. See
      `## Source Verification Findings` F-8 in this plan.
    - **The filter is on the open status only.** Contained and closed findings must not
      appear, because the console derives its severity tiles and its deploy-gate input from
      this list, and a contained finding still in the list would be exactly the stale verdict
      this phase exists to stop.

    Both the run identifier and the strategy identifier are selected because the console
    groups findings under coverage rows by strategy, and because the run identifier makes the
    correlation exact rather than approximate.

    **The correlation.** After fetching, build the list in the same dict-comprehension style
    as the three above, then recover each finding's description in Python from the snapshot
    that came back on its own row. Match an entry when its attack vector, its probe message
    and its turn count all equal the row's. Take the first match's description if it is a
    non-empty string; otherwise leave the description null.

    Correlating against the finding's **own run** rather than against the latest run is a
    deliberate strengthening of `23-UI-SPEC.md § 3.2`, which proposes matching against the
    latest run's snapshot. The join makes the exact run available for free, and matching
    across runs would let a description from an unrelated run attach itself to a finding
    whose probe text happens to repeat — a wrong explanation attached to a real finding is
    worse than no explanation, because the operator has no way to tell it is wrong.

    **The fallback is null, not a synthesised label.** `23-UI-SPEC.md § 3.2`'s prose suggests
    falling back to a generic label built from the attack vector, while the same section's
    declared response shape types the field as nullable. The declared shape wins. A service
    that manufactures presentation copy makes it impossible for the console to tell a real
    description from a synthesised one, and the console already has locked copy for the
    missing case (`23-01-PLAN.md` OD-5). This is OD-5 extended, and it is the reason the
    correlation can never block anything: description is explanatory, the identifier is what
    contain needs, and they travel independently.

    Guard the JSONB defensively. The snapshot column is nullable, its entries are
    caller-shaped dictionaries, and a malformed entry must not raise inside a read path that
    the deploy gate's console mirror depends on. A correlation that throws would take the
    whole programme read down with it, including the coverage table.

    **The return and the log.** Grow the returned dict from three keys to four, leaving the
    existing three byte-identical. Extend the existing structured log with one additional
    count of open findings, in the same style. Add nothing else to the log: probe messages
    are adversarial prompt text and agent responses can contain whatever a customer typed,
    and neither belongs in a log line.

    Extend the module docstring with two sentences: what the fourth key is for, and the fact
    that the description is recovered rather than stored, so a future reader does not go
    looking for a column that has never existed.
  </action>

side-effect lists at `test_redteam_programme.py:285, 318, 338`. A fourth query exhausts the

the identical failure class one file over, and it is in the plan because it was read, not
because it was documented.

**F-8 — The suggested statement sorts severity backwards.**
`23-PATTERNS.md`'s draft statement for this query ends with a descending sort on the severity
column. That column is declared TEXT with a four-value check constraint
(`0012_red_team_programme.py:88`), so a descending sort orders it lexically: medium, low,
high, critical. The critical finding — the only severity that shuts the deploy gate, and the
one the console renders in its banner — would sort last. Replaced with an explicit rank, and
the substitution is one of the two mandatory guard-removal demonstrations.
