<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted public browser → feedback route | Anyone can load this widget. Everything it sends is attacker-controllable; the route's own validation is the only authority. |
| terminal response event → widget state | A server-emitted identifier is stored and later sent back. The widget must not treat it as anything but an opaque correlation key. |
| customer opinion → an operator's aggregate | These rows become the customer-satisfaction and thumbs figures an operator reads in the Live region when judging whether the agent is working. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-WF-01 | Tampering | forged rating for another message | medium | accept | The message identifier is a body field on a route that does not bind it to the caller's session — that is the route's pre-existing shape (`schemas/widget.py:118`), not something this plan introduces. Bounded by the agent-scoped token the route validates first (`widget.py:794`) and by the rate limit. The residual is feedback rows only: no read, no mutation, nothing returned. Logged as a follow-up alongside `T-23-GA-02` rather than left implicit. |
| T-23-WF-02 | Denial of Service | rating flood from one browser | medium | mitigate | Two layers. Server side, sixty per minute per agent in a dedicated key namespace, already closed as `T-21-02-03`. Client side, the per-message submission cap this plan adds, which stops a customer toggling between two ratings from writing a row per click — the case the server limit permits and the aggregate is most distorted by. |
| T-23-WF-03 | Tampering | out-of-range rating or score | low | accept | The rating is a two-value literal and the score is bounded one to five in Pydantic, backed by check constraints in migration 0009. Already closed as `T-21-02-04`. The widget sends the schema's exact shape; a body-shape assertion in Task 1 keeps it that way, but the client is not the control. |
| T-23-WF-04 | Tampering | a metric this phase renders, skewed by this phase's own writes | medium | mitigate | `metrics_service.py:92-99` computes the thumbs rate over all feedback rows, so a message rated and then scored is weighted twice. Verified this session; `23-UI-SPEC.md` accepted the duplicate as unexamined. The approved interaction ships unchanged (it is a checker-approved contract), the submission cap bounds the skew to exactly twice for one message, and the effect plus its proper fix — a uniqueness constraint and an upsert, which is a migration and therefore out of this phase's scope by its own rule — are recorded in `23-01-PLAN.md` OD-7, in `23-VALIDATION.md`, and as a follow-up. The satisfaction average is unaffected: line 95 filters the null-score row out. |
| T-23-WF-05 | Information Disclosure | customer text in a feedback payload | low | mitigate | The body carries two identifiers, a two-value literal and an optional integer. No message text, no name, no address. Asserted by a body-shape gate that counts keys rather than checking for the absence of specific ones, so an added field fails the gate whatever it is called. |
