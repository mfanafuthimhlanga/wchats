<objective>
Refactor capability enforcement so the dispatcher (14-08) can run the *authorization decision* first and the *side-effecting rate-limit increment* only on a fresh (non-replay) call (the structural half of WR-01), and harden the Redis path (WR-04 TLS, IN-01 pipelined INCR/EXPIRE), the constraint check (IN-02 falsy-zero), and the blocking-I/O offload (WR-03 for enforcement.py + audit.py).

The actual reordering happens in 14-08; this plan provides the building blocks and keeps the legacy `check_capability_envelope(agent_id, skill, args)` working as a facade so the still-live 14-04 dispatcher and `test_capability_enforcement.py` stay green.

Split:
- `check_capability_access(agent_id, skill) -> tuple[dict, str | None]` — reads the envelope row, coerces to a JSON-safe snapshot (existing `_json_safe`), applies the fail-closed checks ONLY (no_envelope_row, disabled). NO Redis, NO INCR, NO side effects. Returns `(snapshot, denial_or_None)`.
- `apply_rate_and_constraint_checks(agent_id, skill, snapshot, args) -> str | None` — the side-effecting half: rate-limit INCR (pipelined with EXPIRE) and max_amount_cents constraint. Returns `denial_or_None`.
- `check_capability_envelope(agent_id, skill, args)` — RETAINED facade: calls access; if denial, return it; else calls rate/constraint and returns. Same return contract as today.

Purpose: enable the WR-01 reorder in 14-08 without breaking the current commit, and close WR-04/IN-01/IN-02/WR-03 for these two modules.
Output: refactored enforcement.py, offloaded audit.py, a REDIS_TLS_INSECURE config flag, and tests.
</objective>
